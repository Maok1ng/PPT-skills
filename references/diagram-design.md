# 易讲、可编辑的图解

## 先确定这张图要解释什么

总览图回答“有哪些部分，怎样连接”；流程图回答“先做什么，分支条件是什么”；模块图回答“接收什么，执行什么，交给谁”。选择其中一个为主，不将架构、全部工具、字段和异常情况塞在一页。

先写一句可口述的结论，再保留支撑它的必要节点与箭头。标签优先写业务动作，代码名只在理解实现时有必要才附上。新增图旁边通常一两句解释即可；字段定义、调用细节、完整提示词和局限进入备注或备份页。不要为了凑“科研风”添加无信息图标、阴影或复杂装饰。

## 原生对象的选择

| 内容 | 首选对象 | 需要核对 |
| --- | --- | --- |
| 流程、架构、职责边界 | 原生形状、连接线和文本框，按模块分组 | 方向、分支、输入输出；分组后仍可进入编辑 |
| 方法比较、模块职责、技术栈 | 原生表格 | 表头、行列关系、单位、原始数值 |
| 数学定义、推导 | 原生数学公式及相邻符号解释 | 分数、上下标、求和范围、变量及前提 |
| 论文实验图、定性结果、截图 | 保留论文原图并标注来源 | 图例、坐标、比例、上下文不能被裁掉 |

PNG 或作为图片插入的 SVG 即使很清晰，仍是图片。文字轮廓可以改路径但不是可编辑文字。用户明确要可编辑公式/流程图时，不能静默替换为图片；保留真实限制说明，使用能够支持所需对象的导出方式。

## 简化而不改错

以主路径为骨架，通常先保留少量核心节点；同层节点对齐，用留白和细线分组。方框仅在表示模块、容器、数据对象或边界时使用。已有图复杂时，可移走重复标签、字段样例和次要接口，不能删除决定机制的条件、反馈环或证据边界。

箭头要有真实语义：数据流、执行顺序、监督关系等不能混成同一种无标签的箭头。并行、串行、循环、分支以材料或实现为据；没有自动返工机制就不画自动返工环。图标风格参照当前页面，不强制加入机器人或人物。

项目类汇报若扩展到提示词/Agent 设计，可用“角色职责 → 输入与依据 → 行为约束 → 输出格式”的图概括。输出契约、校验、审计、日志分别描述实际作用；提示词要求不等于代码强制，完成执行不等于审计通过。论文没有这些机制时不要为套图而添加。

## 公式页要让人能读出来

先说明指标或变量的业务/研究含义，再展示公式，最后用已有证据中的数值或一个明确标注的示例解释。不能只摆 R、N、S 或 JSON 字段让听众猜。

例如指标页应说明：求和针对哪些有效记录、订单号为何去重、分子分母是否使用同一范围、分母为零如何处理。币种、数据来源和“样例/实测”明确区分；数据不明就不补人民币等单位。公式太密时按逻辑分步解释，保留必要推导而非一律删掉。

## 配色和字体

新建同济论文稿保持白底、黑色正文、宋体风格与浅灰页脚。浅灰用于分组，细线用于关系，不把深蓝/黑色大底或彩色卡片作为默认。用户指定其他框体颜色时只在对应范围使用；彩色论文原图和校标保留原色。

全稿使用少量明确的字号层级。标题先写清完整结论，不靠大号英文字段制造重点。内容放不下时先删减重复信息或重新组织，不能把文字统一缩成不可读的小字。导出后逐对象检查文字和连接线，公式转换后再核对一次。
